# Agent Note: PDF 滚动中的可见需求与有限任务提交

Status: implemented

## Problem

用户的 baseline / step1 各有 9 个成功场景；普通文本滚动、真实 PDF 滚动及手形拖动的空白面积积分基本不变。用户也观察到快速滚动时中间页面持续空白。真实 PDF 的 `real-pan` 两版全部 `final_timeout`，step1 采样在途任务峰值为 23–24；末帧已清晰，但直到超时仍不满足任务空闲条件。供电、温度及后台负载未控制，不能将 CPU 降幅全算作代码收益。

连续滚动只查已完成整页缓存，新的整页需求等待停止滚动 120 ms 后才再启动 150 ms 预加载 timer；高倍路径可反复提交不同视口区域，没有整体任务上限。首步的同键去重无法限制这些不同键。

## Decision

复用现有单次 QTimer，将可见需求合并为下一次事件循环执行。普通滚动、首屏 cache miss 和高倍 cache miss 都可触发需求，输入不再重启并推迟这个 timer。整页 paint 路径仅查缓存，缺失时返回背景并请求异步处理，不执行 MuPDF 或等待 worker。

每个 DocumentViewport 最多持有一个已提交任务（包括等待线程池和等待主线程完成回调的阶段）。完成后重新检查最新可见页面，不为滚动经过的位置保存任务队列。当前可见页优先于原有相邻页预取；Qt6 连续滚动时不提交相邻页，停止后才允许原有范围。没有新增低清预览或扩大完成缓存。

所有文档视口共享主线程管理的提交额度：`clamp(idealThreadCount / 2, 1, 2)`，上限为 2，低核设备为 1。等待列表仅包含每个视口一个 QPointer，按进入顺序提供机会，任务完成、等待者撤回及视口销毁驱动下一次检查，不依赖周期轮询。仍使用原有 QtConcurrent 全局线程池，不新增线程池或提高其线程数。这是基于单视口已有 23–24 个在途任务的保守起点，不声称该参数是所有设备的最优值。

提交前预留预计输出像素，按 PDF points、DPI 和取整余量估计；同时执行的视口请求合计预算为 64 Mi 像素，单任务沿用原有整页 32 Mi / 区域 48 Mi 像素约束。只有一个任务时允许其独占额度，避免估算余量阻止合法任务。预留直至 worker 已结束且回调已取得结果，取消等待后才归还。该额度仅约束视口渲染输出，不是进程内存上限：MuPDF pixmap、QImage、QPixmap 转换、store、完成缓存和缩略图有各自成本。缩略图和搜索不受本次提交额度管理。

平移时检查当前在途请求是否仍与视口相交；完全离屏则标为 obsolete。worker 在打开 provider 前及光栅化前读取标记；尚未开始的无用请求可以直接退出，仍部分可见的任务允许完成。已进入 MuPDF 的任务不在本次实现中强制中断，每个视口因此最多等待一个旧任务，而不是等待滚动积累的长队列。失效和文档切换继续使用原有 source/page/DPI 身份及共享 generation；旧 owner 的回调不能释放新 owner 的身份。

渲染失败按当前需求记录，不因完成回调立即无限重试；平移、缩放、内容失效后允许重新尝试。主题转换仍位于主线程完成回调，热点页解释/解码缓存和手形截图增量更新另行处理。

缓存淘汰保留当前需求所用的结果，按 source/page/DPI 身份及可见区域判断，优先删除其余旧条目。原有“距离刚完成的 PDF 页码最远”规则在拼接、重排文档中可能让两个当前需要的结果互相淘汰；完成后继续调度会将其放大为持续渲染。整页保留可见页与当前允许预取的邻页，区域缓存为每项可见需求保留一个完整覆盖结果。若区域缓存全部用于当前可见内容，则不提交无法保存的新结果，等待视口变化释放空间；维持现有容量预算，不增加缓存以回避该边界。

## PDF 结构证据

用户授权读取的真实 PDF 与报告哈希一致，为 8,818,641 字节、85 页；扫描得到的 MediaBox 为 595.22 × 842 pt（A4）。直接对象扫描识别 9 个图像对象，最大为 317×104；成功解压的 Flate 内容约 18.7 MB，包含大量路径操作。该扫描未使用完整 PDF 对象解析器，不能据此断言具体渲染耗时归属，但未支持“超高分辨率大图”为唯一原因。

现有真实 PDF 高倍报告中，成功输出像素合计约 4.33 MP，明显不能把总等待解释为整页高倍位图分配。区域渲染仍执行页面内容，解析复杂度和任务积压需要分别观察。本次不修改或提交用户 PDF、原始 benchmark 输出及文件路径。

## Alternatives considered

| 方案 | 优点 | 本次选择 |
| --- | --- | --- |
| 仅去掉 120/150 ms 等待 | 直接减少滚动中新内容的启动延迟 | 会放大不同区域请求的积累；与有限提交、最新需求重查共同实施 |
| 每次输入都把新可见页加入线程池 | 实现直接，空闲硬件可提高吞吐 | Surface 实测已有 23–24 个在途任务；不保留过时需求队列 |
| 每个视口增加独立线程池 | 可以隔离缩略图排队 | 多视口会乘倍增加线程和 provider，维持共享线程池并限制提交 |
| 一开始使用 display list 或独立预览 | 可减少页面解释次数或提早显示低清内容 | 增加常驻资源或重复生成成本，需在有限调度后单独衡量 |
| 同时改变手形截图合成 | 可处理拖动中新暴露区域 | 涉及笔迹、对象层次及截图覆盖探针；本次保留现有手形路径，不把它的空白宣称为已解决 |

## Testing

扩展现有手动 `--test-pdf-render-lifecycle`：首个 settled miss 不同步渲染；阻塞 worker 后连续 40 次移动只保留一个已提交请求；整页和区域都在 scroll flag 持续为真时完成最新可见内容；离屏排队结果不入缓存；多个视口共享额度、等待者撤回重入、完成后全部取得进展并归还像素额度。原有主题、文档切换、取消及重复页检查继续保留。

功能测试仍由用户下载包后手动执行，遵循[手动验证决定](../process/2026-11-27-pdf-benchmark-manual-validation.md)，不加入 Actions 上传条件。原生 benchmark 探针、runner、语料和统计协议保持不变，可继续对比保留的 baseline / step1。编译和功能验证结果在交付时单独说明；没有 step2 实测数字前不宣称收益。

缓存检查将原 PDF 页面按 2、0、1 排列，并用其他来源的页码 1 填满旧缓存，验证整页与区域加载均能保存所需的 2、0 并停止调度。另将区域缓存容量限制为一项，验证已有可见覆盖不会因另一可见页缺失而被反复替换。

## Consequences

可见整页需求不再等滚动结束才启动，快速高倍移动不再为每个区域追加后台任务；最慢任务仍可能决定新需求等待时间。一视口串行会降低可充分并行设备的吞吐，换取低端设备的计算量与在途内存控制；是否改善首屏和快速跨页需要实测。

普通快速滚动从“多数经过页根本没渲染”变成“途中可以提供内容”，CPU 总工作量可能高于此前，不能要求空白显著下降同时无条件保持原来只绘制首尾的调用数。需要一起检查空白积分、CPU、延迟长尾和峰值内存。

全局线程池中的其他任务仍可能延迟 PDF；执行中 MuPDF 不能在本次实现中中断；provider 打开、页面几何查询、主线程深色转换和 QPixmap 转换未全部优化。全应用资源预算和截图增量合成仍属于后续工作。
