# Agent Note: 性能优先的 PDF 加载优化提案

Status: proposed

## Problem

用户要求在实施前按 README 的 Why SpeedyNote 重新审视方案。[README](../../../../README.md) 的第 25–43 行将低端硬件上的高频笔输入、大 PDF 快速打开和小内存占用并列为产品目标。优化必须同时评估输入响应、内容到达时间、总计算量和内存，不能仅凭空白减少或 FPS 上升判断成功。360Hz 在 README 中指笔轮询/输入，不是 PDF 需要每秒完整绘制 360 帧；该描述也不构成本次环境的实测结果。

审查基线仍为 `2f65852`，带测量工具的对照构建为 `68ac33a`。本篇替代[初版提案](../../rejected/architecture/2026-11-27-pdf-scroll-rendering.md)的实施顺序，保留其代码审查事实和正确性约束。请求去重、失效范围与完成重绘已有[首步实现](../../implemented/bug-fix/2026-11-27-pdf-render-request-lifecycle.md)，尚待原生编译及功能测试；整体阶段未完成。测量代码另见 [PDF Benchmark 决策](../../implemented/testing/2026-11-27-pdf-benchmark.md)，baseline 由用户自行采集，目前没有性能实测结论。

初版的问题是将独立预览生成提前，减少无效工作和内存控制放在后续阶段。新增预览会多一次页面执行、可能多次图片解码、分配与拷贝；低 DPI 不能保证解析和解码也按像素比例变便宜。持续预取和增加 worker 会与笔输入、缩略图、搜索竞争 CPU 及内存。需要用实际成本决定是否值得增加这些工作。

### 重审发现的额外约束

- `DocumentViewport.cpp:21495` 绘制同页、同 DPI 的所有缓存区域，仅与整页矩形相交判断，多个重叠区域会提交重复绘制。Qt 仍可能裁剪不可见部分；重复像素处理的实际占比尚未测量。`21737` 和 `5748` 的完成回调还请求全窗口 update。增加缓存和任务数可能同时放大结果处理与绘制成本。
- `MuPdfProvider.cpp:285` 在 MuPDF pixmap 之外分配 QImage 并逐行复制。后台位图、主线程显示位图及转换期间的共存必须计入内存峰值。仅约束最终缓存不足以控制进程内存。
- `ThumbnailRenderer.cpp:263,394,413` 的最终缩略图包含笔迹和对象，不能直接拿来充当 PDF 背景，否则会重复显示或带入过时注释。第一阶段也不为获取背景而触发额外缩略图生成。
- 视口、缩略图和 PDF 搜索都使用普通 `QtConcurrent::run()`。PDF 专用线程池可隔离排队，但不能保证 CPU 不争用；每个视口各增加几个线程也不能代表全应用并发受控。
- `visiblePages()` 已通过布局缓存和二分查找处理单/双列大文档；`ensurePageLayoutCache()` 使用尺寸元数据以避免加载全部页面。调度不能退回逐页扫描，也不能在每次滚动事件中大量触发 `Document::page()` 的懒加载。
- 手势截图与局部脏区绘制是现有性能设计。修复手势空白不能简单删除快速路径，恢复每个输入事件都重绘全部笔迹和对象。

证据：[DocumentViewport.cpp](../../../../source/core/DocumentViewport.cpp)、[MuPdfProvider.cpp](../../../../source/pdf/MuPdfProvider.cpp)、[ThumbnailRenderer.cpp](../../../../source/ui/ThumbnailRenderer.cpp)、[ViewportPerfMonitor.h](../../../../source/core/ViewportPerfMonitor.h)。行号按基线解释。

## Proposal

### 目标与取舍

以低端参考设备上的相同 PDF、相同交互和相同显示质量比较基线，优先保证笔输入及 UI 的长尾响应，再缩短真实内容和目标清晰度的到达时间，并控制 CPU 总时间、内存峰值与持续功耗。额外缓存或计算可以换取等待减少，但必须列明收益、代价和预算；不能把耗电、发热与输入停顿藏到后台。

明确撤回初版中的默认参数：32–50 ms 的调度周期、0.5–1 MP 独立预览、前方 1–2 页、固定两个 worker、512–1024 像素块都没有实测依据，不作为当前实现要求。它们只能在对应机制被证实有价值后成为实验变量。

### 第一阶段：测量与确定性减少浪费

1. 用独立可关闭的 [PDF Benchmark](../../../../benchmarks/pdf/README.md) 固定语料与操作轨迹，保存 `68ac33a` 基线程序及依赖。用户已授权在自行采集 baseline 的同时实施首步优化；只有两者完成比较后才能判断收益。现有 ViewportPerfMonitor 继续用于交互观察；短时 HUD 不能替代内容覆盖、完整长停顿与资源记录。新基准采用有限 trace，不在每个笔事件输出日志；请求阶段和资源字节分解在需要解释具体瓶颈时增加。
2. 统一整页和区域的已完成/在途去重，避免后台同一请求重复执行，也避免主线程与 worker 同时生成同一结果。把非 tiled prune 对共享 generation 的误触发修正为仅影响应失效的内容，保留仍有效的完成结果。
3. 视口改变时只更新最新需求并合并调度通知；空闲 worker 立即处理当前缺失内容。繁忙时更新有限的待处理集合，不为每次 wheel/paint 追加 task。任务完成后按最新需求继续调度；没有需求时不靠周期 timer 空转。处理频率若仍需限制，再以主线程耗时决定节流参数。
4. 可见需求不经过停止滚动后的两级等待；缓存未命中不在 paintEvent 中执行 MuPDF。启动、源文件解析、页几何及请求快照中的懒加载也要检查主线程成本，不能仅把最终光栅化标为异步就认为整个加载过程无阻塞。
5. 深色转换及图片区域处理采用请求快照和 worker 所属 provider，避免主线程再次执行页面。重复结果在重型后处理前识别；完成回调只处理仍需要的图像。QPixmap 转换仍可能耗时，必须计入主线程完成回调预算。
6. 结果到达后合并重绘通知，计算当前视口内实际变化的脏区。画面不相关的预取结果不触发全窗口 update。避免同一可见位置重复绘制多份完全覆盖的缓存；覆盖关系在缓存或视图改变时更新，不能把复杂区域运算搬到每个笔事件里。
7. 建立应用内可管理的 PDF 图像预算及在途资源预留，联合考虑多个可见视口和缩略图。请求执行前检查预计像素和转换峰值；预取不得挤走可见内容。MuPDF store 目标、最终缓存字节和进程总内存分别统计，不把它们混为一个上限。

本阶段保留普通缩放整页、高倍/超大页区域的分工。普通页一次完整渲染可使后续页内移动直接命中缓存，不应在没有测量时将所有缩放统一改成小块。

### 第二阶段：在相同预算内复用已完成工作

- 缩放期间保留有用的已生成纯 PDF 图像，作为临时显示；不为每个页面强制额外生成低清图。缓存跨质量复用必须有正确的源版本、原始页映射和配色身份，并保持总字节预算不增加；不保留所有历史缩放档位。
- 图片区域几何按页及内容版本复用。同页多次执行占比较高时，优先对比热点页 display list 与有预算的 MuPDF 资源保留策略。保留的资源以减少重复解析/解码为目的，不能无条件撤销 `trimStore()` 的历史内存保护。
- 只有当前内容处理有余量、方向稳定且已有覆盖即将不足时，准备一个有限的相邻候选范围。前进方向优先，已经读过的后方区域按最近使用保留；不固定双向额外渲染若干整页。笔输入繁忙、可见请求积压、内存压力或方向突变时减少或停止推测性任务。
- 预取量受屏幕范围、渲染成本与剩余预算共同限制；快速滚动不意味着无限扩大预取。跨越很多页时更新到当前范围，省略已错过且尚未开始的中间请求。
- 手势期间依旧复用现有合成截图；采用目标视口更新需求，只在新区域或内容结果需要展示时更新受影响区域，或按受控频率刷新合成缓存。新 PDF 内容与笔迹、对象、遮挡必须按现有层次合成，不能直接覆盖旧截图中的笔迹。具体选择通过主线程合成耗时与边缘等待的对比确定，不承诺这一阶段完全消除所有冷页空白。

“复用旧图”只能覆盖其本来包含的页面或区域，不能生成从未访问过的内容。目标是减少不必要的空白和真实等待；任意首次跨页都零等待不作为无成本承诺。

### 第三阶段：只有测量证明必要才增加机制

| 测量结果 | 候选优化 | 必须一起验证的代价 |
| --- | --- | --- |
| 同页重复解析/解码占主导 | 热点 display list、有限资源保留、请求的 worker 局部性 | 首次构建、不同 worker 的重复资源、峰值和空闲内存；线程锁约束 |
| 重叠大矩形反复光栅化占主导 | 只请求缺失带状区域，或固定网格块 | 小任务调度与合成成本、重复页执行、接缝；两种方案比较后再决定 |
| 冷页首内容仍慢，低清生成实际明显更便宜 | 有预算且按需的独立预览 | 与直接生成目标清晰度相比的总 CPU、首次清晰时间及峰值内存；文本/扫描件分别评估 |
| 帧耗时主要在图像拷贝/合成 | 减少重复 draw、转换次数与可避免复制 | 图像所有权、跨线程生命期、格式/平台兼容；不预先承诺 zero-copy |
| 排队占主导且低端输入有余量 | 调整优先级、隔离队列或有限增加并发 | 全应用 CPU 竞争、MuPDF 全局锁、额外 provider 与缓冲内存 |

网格和 display list 不是必然绑定：前者减少重复光栅面积，后者减少重复解释页面；应逐项测量，再组合。独立预览同样不被永久排除，如果它以小而受控的代价明显缩短冷页等待，就符合性能目标。

## Alternatives considered

| 方案 | 最强理由 | 当前取舍 |
| --- | --- | --- |
| 初版默认独立预览加多页预取 | 可较早出现页面内容，隐藏部分高清等待 | 未证明低端设备上的总成本；取消其第一阶段必选地位，保留为条件性实验 |
| 一开始统一固定网格 | 同页平移复用重叠区域，块级优先级清楚 | 普通整页命中路径可能变复杂；任务与页执行次数可能增加。先证实重复光栅占比 |
| 只改定时器 | 可直接减少启动等待，工程成本低 | 仍有重复工作和截图早退；提高请求频率可能扩大现有浪费。与去重和工作量限制一起处理 |
| 尽量少缓存、每次重新计算 | 常驻内存低 | 反复解析、解码会影响输入响应并增加功耗。保留受预算限制且有复用收益的数据 |
| 全部移到后台并扩大线程池 | 降低部分主线程阻塞，提高并行机会 | CPU、内存带宽及全局锁仍共享；主线程结果转换与合成成本还在，不能作为性能结论 |
| 删除手势截图路径、每帧绘制全部场景 | 实现上容易显示新到达内容 | 与低端输入、局部脏区和截图复用设计冲突；保留复用并控制更新范围 |

## Acceptance criteria

### 第一阶段必须成立的行为

- 持续滚动期间当前缺失内容可得到调度；同一键不重复渲染，队列与在途预算有上限。新需求更新不会迫使所有有效执行中任务一律作废。
- 无 PDF 需求时没有新增周期唤醒；离屏预取结果不引发无关重绘。所有可见分屏均能获得进展，不能只优化一个视口。
- 主线程绘制路径没有 PDF 光栅化、逐像素深色转换或等待 worker；结果处理和页面加载另外计时，不掩盖其成本。
- 高倍清晰度、尺寸预算、DPI/DPR、源映射、暗色和文档切换保持正确。笔迹与对象不因截图增量合成而丢失、重复或错位。

### 性能判定

| 维度 | 测量内容 | 判定原则 |
| --- | --- | --- |
| 笔输入与 UI | 输入处理与分发间隔、长任务、paint 及完成回调的 P95/P99 | 开启 PDF 后台任务时与基线比较，不能靠牺牲输入获得翻页改善；软件时间戳不能冒充物理笔到屏幕延迟 |
| 阅读等待 | 冷/热首屏内容、目标清晰度时间、空白面积随时间变化 | 分开报告，不能把模糊预览出现当成高清加载完成 |
| 工作量 | 固定浏览轨迹的进程 CPU 时间、页执行数、光栅像素数、重复/过期结果 | 第一阶段优先减少重复工作；每个推测性机制注明实际增加的工作及等待收益 |
| 内存 | 应用缓存、在途像素、provider/store、进程峰值及静止后的保留量 | 共享预算不会随 worker、标签页或每个视口独立倍增；实际进程峰值单独验收 |
| 持续使用 | 长时间滚动后的输入延迟、温度/降频、可用时的能耗数据 | 短时高吞吐不掩盖低端设备持续退化；不能仅由 CPU 利用率推算电量 |

参考设备至少覆盖 README 指向的低端 Windows 类设备，并在支持的低端 ARM64 平台验证；当前环境没有这些测量。采用文本、扫描/JPEG2000、复杂矢量、超大混合页面，复用同一录制轨迹比较冷启动、普通跨页、高倍同页、回看、书写与预取并行、缩略图/搜索并行、多视口及明暗模式。

测量前固定文档、DPR、窗口、构建和供电条件，重复采样确定噪声范围。优化在参考设备上必须带来可重复的等待改善；输入长尾、首次打开及内存退化需单独说明和处理，不能用平均值覆盖。没有实测就保持 proposed，不宣称满足极致性能。

## Risks

- 完全不预取无法让所有未访问页面即时显示；合理预取仍有价值，但效果依赖文档与阅读速度。
- 收紧并发和保留旧图可能改善低端响应，却降低高端设备吞吐；具体默认值需要跨设备数据。
- 热点 display list 和解码资源并不全能精确计入应用图片预算，要结合进程内存与生命周期验证。
- 调度器过度通用化、复杂预测或每帧覆盖集合运算会引入自身成本。实现只覆盖现有整页与区域需求，新增层次须有测量理由。
- 将所有冷页操作异步化可能增加空任务调度及首帧往返；请求应及时开始，不能把现有 timer 等待替换成新的无条件延迟。
