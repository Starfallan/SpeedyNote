# Agent Note: PDF 滚动空白与渲染等待的审查及优化提案

Status: rejected — 默认先增加全页预览及预取的实施顺序缺少低端硬件成本依据，由性能优先提案替代。

## Problem

本篇保留初次审查的代码证据与原提案理由；实施顺序不再适用。当前建议见[性能优先的 PDF 加载优化提案](../../proposed/architecture/2026-11-27-pdf-performance-first.md)。被否定的是未经测量即把独立预览列为第一阶段必选项，并非以下控制流问题的存在，也并非永久排除预览。

审查基线为 `2f658529b33642404bb659b47b8e536a1b1a5a55`，也是审查时的 HEAD。用户报告普通缩放跨页、高倍缩放同页移动均出现空白与等待。范围包括滚动触发、手势绘制、整页与区域渲染、后台任务、缓存、深色模式和现有测试。

本记录是静态审查及待实施方案，没有修改运行代码，没有编译、运行应用或进行性能实测。代码能够证明以下控制流和资源策略；各因素在用户 PDF 上的耗时占比、预取参数和实际改善幅度仍需测量。

### 1. 普通缩放：滚动期间只读缓存，停止后可能阻塞主线程

`DocumentViewport.cpp:1452` 的 `setPanOffset()` 通过 `onScrollActivity()` 标记滚动。Qt6 总是将 `m_scrollActive` 设为 true；Qt5 的离散滚轮是例外，直接允许同步渲染。`renderPage()` 在滚动期间仅调用 `lookupCachedPdfPage()`；未命中时保留纸张底色，不会立即提交当前新页的渲染任务。

停止滚动后，120 ms 的 settle timer 才执行 `onScrollSettled()`，然后启动另一个 150 ms 的 PDF preload timer。这里必须区分两种等待：

- 当前普通整页在 settle 后的重绘里可以立即进入 `getCachedPdfPage()`，由主线程同步渲染。因此不能把当前页等待一概描述为 270 ms；它可能是停止前的持续空白、120 ms 等待及同步渲染耗时。
- 邻页异步预取沿 settle 路径需要约 120 + 150 ms 才开始，实际事件循环延迟还可能更长。连续滚动会反复推迟 settle，已缓存范围以外的页面得不到持续预取。

这套等待策略早于此次合并；`26b840a` 引入统一 scroll-activity gate 和延迟维护。`2f65852` 的差异没有新建这一整页等待机制。

证据：`source/core/DocumentViewport.cpp:1475,1498,5482,5569,20638`；`DocumentViewport.h:3993,4001`。

### 2. 高倍缩放：可见区域渲染没有形成真正的前向预取

`doAsyncPdfTilePreload()` 只遍历 `visiblePages()`，并要求页面与当前视口有交集。每个可见页生成一个随视口移动的大矩形，周围增加 160 个物理像素的余量，并按 32 page units 对齐。它不是固定网格小块缓存。

已缓存区域完全包含当前可见矩形时直接跳过。也就是说，只有用户已经越过已有覆盖范围，才请求下一块；余量主要延后未命中，并未用于在边缘到达之前刷新前方内容。下一页尚未可见时没有请求，跨页自然无法提前显示其内容。

`drawCachedPdfTiles()` 有缓存未覆盖时启动 150 ms timer 的逻辑，因此高倍普通滚动并非完全等到停止才渲染。但期间新露出的条带仍可能空白，且 settle 路径会重新启动同一个 timer。必须将这个自触发行为与整页路径区分。

证据：`DocumentViewport.cpp:21420,21478,21584,21623`；`PdfTileGeometry.h:97`；`DocumentViewport.h:3967,3970`。

### 3. 缺少独立的预览层，缩放还会清空可暂时显示的内容

整页和区域缓存均按目标 DPI 匹配。进入 tiled 模式后只绘制区域缓存；没有全页低分辨率预览覆盖尚未到达的区域。缩放改变或模式跨越会清空相应缓存，手势结束也清空 PDF 缓存。

因此后台渲染尚未完成时没有可用于阅读定位的页面内容。`4f526fb` 曾移除 `lookupAnyCachedPdfPage()`，提交说明指出其缓存会被清空且 tiled 模式不再填充，属于无效路径。不能只恢复这个函数；预览必须有独立生命周期和生产任务。

证据：`DocumentViewport.cpp:1436,5148,5791,20638`；`DocumentViewport.h:286,323`；`git show 4f526fb`。

### 4. 手形工具和中键拖动：即使后台完成，也不会显示新内容

`beginPanGesture()` 截取当前窗口；移动只更新 `m_gesture.targetPan`，不提交真实 `m_panOffset`。`paintEvent()` 的手势路径平移这张截图，填充截图覆盖不到的背景后直接 return，跳过正常页面绘制。最终位置在 `endPanGesture()` 才提交。

这条路径用于手形工具、中键拖动及部分修饰键滚动。仅调整 PDF cache timer 无法解决它；调度与绘制都必须能使用手势目标视口，并显示后来完成的页面内容。截图含有笔迹和对象，更新它时还需避免对象重复绘制或坐标不同步。

证据：`DocumentViewport.cpp:3255,3900,4440,5178,5210,5230,16161`。

### 5. 后台任务没有完整的去重、优先级和工作量限制

- 整页预取只检查已完成缓存，不检查相同页面的在途任务；多个 preload pass 可以重复提交同一页面。主线程同步渲染也不检查正在执行的后台任务。
- 整页按页面编号递增提交，上一页可能在当前可见页之前，没有显式可见性优先级。
- 区域任务仅对完全相同矩形去重。相邻视口生成的高度重叠矩形仍会分别执行，已有多块区域的并集覆盖也不会通过单块 `contains()` 判定。
- 两条路径直接使用默认 `QtConcurrent::run()`，应用层没有 PDF 专用的有界任务队列或在途像素预算。线程池本身限制执行线程数，但不等于限制所有排队请求及其资源需求。
- 普通平移不更新 generation；与当前视口无关的旧区域任务仍可完成并插入缓存。整页 worker 连开始前的 generation 检查也没有，仅完成回调检查。
- `prunePdfTiles()` 在非 tiled 模式每次执行都会调用 `invalidatePdfTileCache()`，递增与整页共享的 generation。它可因普通 settle 丢弃同一文档、同一 DPI 的有效整页在途结果。

证据：`DocumentViewport.cpp:5618,5655,5688,5754,5844,5921,21568,21648,21741`。

### 6. MuPDF 的解析和解码资源复用不足

每个后台线程仅缓存一个文件路径对应的 provider。每次区域渲染调用 `fz_load_page()` / `fz_run_page()`，没有应用级 display list 缓存；同一页的新区域仍需执行页面内容。矩形输出限制减少了像素分配，但不保证解析及图片解码工作按可见面积同比缩小。

整页和区域任务完成后均调用 `trimStore()`，实现为 `fz_shrink_store(m_ctx, 0)`，要求清除可回收 store 资源，降低字体及图像解码结果的复用机会。扫描件和复杂页面受到多大影响需测量。

清理策略来自 `d2b6096` 的内存问题修复，不能直接全局删除。每个 provider 已设 32 MiB store 目标，但多个 worker、光栅临时缓冲及应用缓存仍需共同预算。

MuPDF 1.24.10 官方 `display-list.h` 明确将 display list 用于减少页面重复解析、分离解析与绘制，并提供 scissor 范围和 cookie。应在后续优化中缓存有限的热点页 display list，保留锁及资源释放约束。

证据：`DocumentViewport.cpp:153,5764,21754`；`MuPdfProvider.cpp:25,431,476,501`；[官方接口说明](https://github.com/ArtifexSoftware/mupdf/blob/1.24.10/include/mupdf/fitz/display-list.h)。

### 7. 深色模式的后处理仍阻塞主线程

两个异步完成回调均在主线程调用 `Document::pdfImageRegions()`，后者最终再次执行 MuPDF 页面内容；之后逐像素转换图像颜色，最后创建 QPixmap。同页不同区域还重复提取全页图片区域。

因此异步光栅化完成不代表图像立即可显示，深色模式可能在结果到达时产生 UI 停顿。可将图片区域按源版本和页面缓存在 PDF 坐标系，复用到不同 DPI；颜色转换移至 worker，完成回调只做身份检查、缓存及显示。具体线程边界不能直接把 `Document*` 传进 worker，应使用请求快照和线程所属 provider。

证据：`DocumentViewport.cpp:5702,21702`；`Document.cpp:1106`；`MuPdfProvider.cpp:543`；`DarkModeUtils.cpp:92`。

### 8. 缓存预算和淘汰策略不适合反复阅读

整页缓存按数量控制；区域缓存将视口像素估算换算为容量，并强制至少 2 项，未对实际缓存字节逐项累加，也未计算在途图像、MuPDF pixmap 和 QImage 复制期间的峰值。因此 192 MiB 的区域预算是估计值，不是整个 PDF 系统的硬限制。

淘汰以源 PDF 页码距离为主。相同页面不同区域无法按最近访问或离视口距离区分，可能淘汰刚读过的区域。多 PDF 来源、重排或重复页面时，源页码差也不代表笔记本中的距离。预取返回的结果还可能淘汰目前可见的缓存。

证据：`DocumentViewport.cpp:5548,5730,5924,5965,21531`；`MuPdfProvider.cpp:285`。

## Proposal

保留高倍区域渲染、真实 provider 几何、源页映射、DPI 计算和大图保护。分阶段改善用户看到内容的时机与实际渲染工作量。

### 第一阶段：持续调度和渐进显示

1. 将重型维护的 settle timer 与可见 PDF 的请求调度分离。滚动开始及可见范围变化立即更新需求；后续按有上限频率的 throttle 调度，不能因不断重启 timer 而无限推迟。32–50 ms 可作为实验起点，不作为性能承诺。
2. 使用有界 PDF 调度器，统一整页、预览和区域任务的去重及优先级。当前屏幕缺失内容优先，随后是滚动方向的近邻，再后是反方向保留区。队列更新时移除已不需要且未执行的任务。
3. 引入独立、有限像素的全页预览，普通及高倍模式共用。按页面实际尺寸同时限制总像素和最长边，不能为所有超大页固定同一 DPI。0.5–1 MP/页、前方 1–2 页和后方 1 页仅作为待实测起点。真正冷页仍需生成预览，不能承诺任意跨页跳转绝无等待。
4. 缓存已有图像时先显示；当前目标清晰度的结果到达后覆盖预览。预览不因纯缩放失效，PDF 内容、页面映射及配色策略变更必须失效。保留已有清晰区域作为过渡显示时，也要检查同一内容版本。
5. 允许当前区域接近已渲染边缘时提前请求前方内容；预取区域必须显式覆盖尚未可见的邻页边缘，不能只扩大已经可见页内部的 margin。预取距离结合滚动速度、观测到的渲染耗时及预算设置上下限，转向后调整优先级。
6. 手势路径使用 targetPan/targetZoom 派生目标视口，并能绘制该处已有缓存及新结果；保留笔迹和对象的正确合成。纯粹加大截图只能延后边缘露出，不能替代这项改动。
7. 普通页面缓存未命中时也由后台完成，避免 settle 后的 `paintEvent()` 同步等待 MuPDF。冷页由预览任务与清晰内容任务分级供应。

预期体验是相邻翻页和反向回看优先显示已有内容，少量未准备好的细节随后变清晰。没有实测前不预估百分比，也不承诺所有 PDF 的即时显示。

### 第二阶段：减少无效工作并控制内存

- 区分内容身份、质量要求和视口需求：内容 generation 用于阻止错误源/映射/主题结果进入缓存；视口变化只更新需求优先级，不能把所有仍有用的结果一律作废。修正非 tiled prune 对共享 generation 的误触发。
- 渲染中任务应尽可能保留仍有价值的结果；完全无用的任务可研究通过 `fz_cookie` 协作取消。当前调用传 nullptr，`watcher->cancel()` 不能当作终止 MuPDF 计算。官方接口提供取消通信机制，但响应速度、对象生命周期和跨线程访问方式需按实际构建版本验证；不能声称即时中断任意解码。
- 从小规模专用 worker 数量开始测量，例如 2 个；限制排队量及预计在途像素。不要以 CPU 核数直接扩大并发。当前页工作必须能超越尚未开始的低优先级预取。
- 将深色模式图片区域收集和图像转换移到后台，缓存页面坐标的图片区域。主线程保留 QPixmap 创建及 UI 更新。
- 以实际图像字节、临时光栅估算、活跃 provider store 和缓存层预算进行控制。保护可见内容，按最近使用及文档空间距离淘汰，兼顾同页位置和多源页面映射。

### 第三阶段：热点页 display list 与固定网格区域

对同页连续移动，评估 512–1024 物理像素量级的固定网格块。缓存键包含源版本、原始页与映射身份、渲染质量档位、网格坐标及配色版本。仅渲染缺失块，按块展示，向滚动方向预取一圈或更多有预算的区域。

固定网格可降低高度重叠的大矩形重复光栅化，但会增加任务数。应与有界调度、热点页 display list 复用共同评估。display list 首次构建有成本，并不自动加速首次冷页或所有扫描图像的解码。质量档位切换也不能长期复用分辨率不足的结果，否则会重新出现放大模糊。

保留现有 MuPDF 全局锁与每个 context 的使用约束。worker 私有缓存是较简单的起点；共享 display list 及 cloned context 属于另一项需要单独验证的实现选择。资源缓存改为在预算压力、空闲或文档释放时回收，不直接撤销所有历史内存保护。

## Alternatives considered

| 方案 | 优点 | 不作为完整方案的原因 |
| --- | --- | --- |
| 将 150 ms 调小或设为 0 | 改动直接，可减少某些启动等待 | 无法解决整页滚动期间不提交需求、手势截图早退、相邻区域未预取和重复工作；可能增加任务洪峰 |
| 单纯扩大缓存数量或 margin | 更容易命中回看区域，已有结构可复用 | 首次未加载区域仍空白；视口大矩形重复渲染和多线程临时内存进一步增加 |
| 每次滚动同步绘制缺失内容 | 不需要引入完整的异步状态机制 | 将等待转移到事件循环，重页容易导致输入和绘制一起停顿；现有 Qt5 离散滚轮即保留了这一行为 |
| 预渲染整本 PDF | 已完成的页面可快速访问 | 大文件首次等待、CPU 和内存成本过高；任意高倍仍需要按需清晰区域 |
| 仅改成固定网格 | 可复用相邻视口的重叠内容 | 未改调度与 display list 时会增加重复解析次数，且仍不能修复截图手势路径 |
| 取消每次 trimStore 并增加线程 | 有机会提高解码复用与吞吐 | 历史内存及并发崩溃约束真实存在；多个 context、光栅缓冲和全局库锁可能抵消收益，应先有总预算及测量 |

## Acceptance criteria

### 调度与正确性

- 连续滚动时有可见需求持续提交；不能必须停止滚动才开始处理新页。
- 同一内容、区域、质量请求不重复提交；可见内容优先于邻页预取；快速跳转后排队工作量受限。
- 手形、中键、普通滚轮、触控板及滚动条均能在交互进行时显示后来可用的内容。
- 缩放时预览可继续显示，清晰区域完成后升级；多源 PDF、重排页面、源文件重连、暗色切换不会显示过时内容。
- 模式切换保留现有尺寸预算与滞回；不同 DPR、旋转页、非零页面原点、实际 provider 尺寸不一致仍映射正确。
- 关闭或切换文档时不存在悬空 worker 访问；取消和结果回调不会删除新请求的登记。

### 性能测量

现有 `ViewportPerfMonitor.h` 测量 paintEvent 时间、帧间隔和绘制路径，没有 PDF 任务端到端时序或内容覆盖率。仅观察 FPS 不足以判断白页问题是否改善。

建议新增可关闭的诊断数据：需求产生时间、入队/开始/完成/显示时间、预览与清晰内容覆盖率、排队深度、取消及重复请求数、整页/区域/display list 命中率、缓存和在途字节、进程内存峰值。区分首屏内容等待与达到目标清晰度的等待，报告中位数和 P95。

用同一批文本 PDF、扫描件（含 JPEG2000）、复杂矢量图及超大页面，分别测试冷/热缓存、普通/高倍、上下连续移动/反向回看/跨页跳转、单/双列及明/暗色。每阶段与基线录屏和日志对比。已命中完整缓存的反向回看应在下一次绘制显示，不再经过 preload timer。

现有 `PdfTileGeometryTests.h` 覆盖区域几何，`DocumentViewportTests.h:389` 的 `testPdfCache()` 主要检查无 PDF 情况下的缓存调用；它们没有验证真实滚动调度、任务去重、预览显示及内存上限。实现时需增加可控慢速 provider / executor 场景的行为测试，并保留真实 PDF 人工验证。

## Risks

- 低清预览在极高倍下仅适合定位，必须持续升级至目标清晰度；扫描源本身没有的细节不能由更高 DPI 恢复。
- 提前计算会增加 CPU、功耗及内存，后台或不可见文档应停止无关预取；方向预测失误时要及时调整队列。
- display list 与保留的解码资源会占用额外内存，32 MiB store 目标不等于单个 worker 总内存上限。
- 固定块需处理边界采样、透明度和图片掩膜，避免接缝。不能以图像肉眼大致正确替代几何验证。
- 手势截图包含 PDF 以外的对象，替换绘制路径属于跨模块行为变更，应单独审查笔迹与对象合成。
- 第一阶段在实际扫描件上的首帧收益未验证，预览也可能受解析/解码耗时限制。若诊断显示该部分占主导，应提前实施热点资源复用。
